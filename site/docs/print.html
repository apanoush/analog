analog

Documentation index

analog is a local-first film grain editor built as a Rust workspace (library, CLI, GUI).

Overview

The engine reproduces four effect blocks, applied in a fixed order:

  1. Film Color Shift
  2. Grain
  3. Halation
  4. Print Simulation

A recipe is the complete, reproducible set of parameters for a render, including a deterministic grain seed. Recipes are the unit shared by the library, the CLI and the GUI, and serialise to the .analog XMP format.

Documentation map

  • architecture.md: crate layout, the render pipeline, the data model, determinism and cross-platform strategy.
  • decisions/: records of significant decisions, each with context, rationale, alternatives and consequences.

Package documentation

Each crate documents its own responsibilities in its src/lib.rs (or src/main.rs) header. Module-level docs describe the individual passes once they exist.

Build and verify

cargo build --workspace
cargo fmt --all
cargo clippy --workspace --all-targets
cargo test --workspace

Architecture

Crate layout

A Cargo workspace separates the engine from its front ends so the GUI’s heavy dependencies never leak into the library or CLI.

CrateRole
analog-coreLibrary: recipe/params data model, image I/O, and (later) the wgpu render engine and WGSL shaders.
analog-cliclap-based command line front end.
analog-guiiced desktop front end.

analog-core is the single source of truth for the parameter model. Both front ends depend on it and must not duplicate parameter ranges or defaults.

Data model

The model is data-first: plain structs with serde derives and documented ranges, so a recipe can be serialised, compared and clamped without any engine present.

  • params::{GrainParams, HalationParams, PrintParams, FilmParams}: one struct per effect block, each with a Default that reproduces the shipped neutral values and a clamped() method.
  • params::{GrainType, PaperType, FilmStock}: the enumerations. FilmStock exposes a stable snake_case id() for recipes and the CLI.
  • recipe::Recipe: the four blocks plus grain_seed, name and schema_version. Recipe::neutral() is an explicit pass-through.

Ranges and defaults are documented per field.

Render pipeline

The documented order is Film Color Shift, then Grain, then Halation, then Print Simulation, ending in a readback. The engine will be a multi-pass wgpu compute pipeline over rgba8unorm textures for the first milestone:

  1. analyze_luminance: GPU atomics produce the image min/max luma; the CPU derives the three adaptive-zone multipliers.
  2. analyze_hue_clusters: four circular-hue centroids into a fixed-point buffer.
  3. film_stock_transform: our own parametric color model (implemented).
  4. Grain: a three-stage pipeline (scatter, blur, apply).
  5. Halation: extract, downsample, upsample_add, composite (implemented).
  6. print_simulation_transform (implemented).
  7. Readback to analog_core::Image.

Grain model

The grain is a three-stage GPU pipeline (scatter, blur, apply), and documented:

  • Noise: an integer hash (Wellons’ lowbias32) over a lattice, bilinearly interpolated, two octaves. Integer hashing is what makes a grain_seed reproducible across backends.
  • Size: grain_amount and grain_type set the noise feature size in pixels (coarse 3-12 px, smooth 2.5-10 px, fine 1-4 px).
  • Zones: luminance_shadows/mids/highlights scale three overlapping smoothstep weights over luma, fading to zero at the deep shadows and near white.
  • Color: per-channel noise offsets, blended toward monochrome by grain_color and directed by color_shift.
  • Softness: a separable box blur (horizontal then vertical) of the grain field, radius from roughness; the composite applies a mild contrast compensation because the field is already low-frequency.
  • Dissolution: clumps the field and, above 10 and 20, adds dust specks and scratches.
  • Focus: with a depth map, in-focus pixels use the sharp field and defocused pixels use the blurred field, mixed by depth_of_field_intensity.

Halation model

A Kawase-style bloom, documented:

  • Extract: pixels above halation_threshold (0-255) with a soft knee, keeping the bright colour.
  • Downsample: a box-filter mip chain (1/2, 1/4, … up to 1/64).
  • Upsample: tent (bilinear) upsample with additive accumulation.
  • Radius: halation_radius selects how many mip levels contribute, so a larger radius produces a wider bloom.
  • Composite: 70 percent additive plus 30 percent screen, a yellow-to-red tint whose hue is clamp(color_tone/100 + (color_shift - 50)/100, 0, 1) (desaturated by halation_color_intensity), highlight protection, and a dither. The tint is exposed as analog_core::tint_rgb so the GUI’s gradient swatch and the render stay in sync.
  • light_spill_intensity is folded into the composite intensity.
  • Depth: with a depth map, halation_background_focus suppresses the glow on the in-focus subject and halation_background_gain boosts it in the defocused background.

Print model

A per-paper tone map applied last:

  • Shadow floor: matte 0.118, neutral 0.06, glossy 0.005, scaled by print_sim_paper_intensity (which is why the full-strength values only appear at paper intensity 100).
  • S-curve: a smoothstep contrast lift, amount per paper (matte 0.10, neutral 0.15, glossy 0.20).
  • Highlight shoulder: identity to a knee, smoothstep to a white point (matte 0.45/0.72, neutral 0.55/0.78, glossy 0.65/0.84), gentle compression beyond. print_sim_highlight_rolloff lowers the knee.
  • Paper tint: warm cream to cool cyan-blue, from print_sim_paper_tint.
  • print_simulation blends the whole effect with the input.

Approximation: the highlight shoulder uses a smoothstep.

Film model

A parametric emulation; no third-party LUTs. Each stock has a Profile (in src/film.rs) applied in shaders/film.wgsl:

  • Lift/gain/gamma per channel.
  • Saturation around BT.709 luma.
  • Shadow/highlight tint, where the warm shadow tint approximates the C-41 orange mask.
  • Black-and-white stocks use a channel mixer and a paper tone.

Deferred: per-image hue-cluster narrowing and baked 33-cubed LUTs. Our 19 profiles are hand-authored approximations.

GPU scaffold

gpu::GpuContext owns one wgpu device and queue, requested with a high-performance preference. passes::GpuImage is a pixel buffer that lives on the GPU; passes::ImageComputePass::run_gpu takes &GpuImage inputs and returns a GpuImage with no readback, and GpuImage::read is the single synchronisation point. Renderer::render uploads the source once, chains the passes on the GPU, and reads back once. Passes compile lazily on first use, and only the pixel format actually used (see decisions/0005-gpu-resident-pipeline.md).

Determinism

Grain must be reproducible: the same grain_seed has to yield byte-identical grain on every run and every backend. This rules out float-noise generators. Grain is produced by an integer-hash PRNG in WGSL seeded from grain_seed and the pixel coordinate, and guarded by golden-image tests.

Image I/O and bit depth

Image holds RGBA pixels in one of two PixelFormats: Rgba8 (4 bytes per pixel) or Rgba16 (8 bytes per pixel). Decode preserves 16-bit PNG/TIFF; encode writes 16-bit for those formats and falls back to 8-bit for JPEG and WebP. JPEG output composites over white because the format has no alpha channel; WebP keeps alpha and is written lossless.

On the GPU each pixel is packed into u32 words: one word for Rgba8 (r | g<<8 | b<<16 | a<<24), two for Rgba16 (r | g<<16, b | a<<16). Shaders that read or write the image declare //@IMAGE_LOAD / //@IMAGE_STORE markers, and shaders::image_shader substitutes the 8- or 16-bit implementation when the pipeline is compiled; each such pass holds both variants. Auxiliary buffers (grain field, bloom chain, depth map) are always 8-bit.

Renderer::render preserves the input depth: an 8-bit source produces 8-bit output and a 16-bit source produces 16-bit output.

PSD files are imported through the psd crate as their flattened 8-bit RGBA image; the crate can panic on some variants, so the call is wrapped in catch_unwind. PSB and PSD/PSB export are not supported.

Camera RAW files (CR2, NEF, ARW, DNG, …) are developed to 16-bit sRGB RGBA through LibRaw on the raw feature (decode only), so they enter the pipeline like any other 16-bit input; RAW is never an output format. See decisions/0007-camera-raw-input.md.

Cross-platform

wgpu targets Vulkan, Metal and DirectX 12 from one codebase; iced renders the UI, and user paths go through the directories crate (see the depth model). The GUI hides the Windows console in release builds (via windows_subsystem). Development happens on Linux/Vulkan; the release workflow also builds Windows and Apple Silicon macOS artifacts. Platform-specific build requirements are recorded in .cargo/config.toml, crates/analog-core/build.rs and the README.

Recipes

A recipe is the shared unit of the library, CLI and GUI. It serialises to JSON (via serde) and to the .analog XMP format (via recipe_io), and the CLI preset subcommand converts between them. The XMP attribute names mirror the internal schema so a preset round-trips faithfully; import is lenient.

Depth model

Focus-based grain and depth-aware halation use a monocular depth estimate from Depth Anything V2 Small (onnx-community/depth-anything-v2-small, Apache-2.0) run through ONNX Runtime (ort). The model is not shipped: the int8-quantised ONNX file (~27 MB) is downloaded on demand into the platform cache directory via the directories crate (~/.cache/analog on Linux, ~/Library/Caches/analog on macOS, %LOCALAPPDATA%\analog\cache on Windows) and loaded from there afterwards.

DepthModel::predict squashes the image to the model’s 518x518 input, applies ImageNet normalisation, runs inference, normalises the output to 0..255 (higher is nearer), and resamples it back to image resolution as a DepthMap. The GPU passes read the depth from an RGBA8 buffer; when no depth map is supplied the host forces the depth controls to zero so the shaders never read the placeholder.

GUI

The analog-gui crate is a single-window iced app. It holds a GpuContext and a Renderer (whose passes compile lazily), keeps the original image plus a full preview proxy and a coarse proxy, and re-renders on parameter changes: the coarse proxy immediately, the full proxy after a 60 ms debounce. Export renders the original at full resolution and writes it with Image::encode.

The preview is an iced canvas (canvas::Program) rather than a plain image widget, so it can be scaled and translated. Scrolling over the photo zooms in and out anchored at the cursor, dragging with the left button pans while zoomed, and a “Fit” button or a double-click resets the view. Zoom is clamped to [fit, 8x], and the pan is clamped so the photo never leaves a gap in the viewport. The view (zoom and pan) is a small, pure ViewTransform in crates/analog-gui/src/view.rs; the canvas program only turns mouse events into new transforms. Zooming upscales the 900 px preview proxy, so fine detail is limited until a higher-resolution preview on zoom is added. This is what requires iced’s canvas feature.

A hold-to-compare control shows the un-effected original while held: press the “Compare (B)” control, or hold B or \, to display the raw source proxy instead of the render. It is built with mouse_area (on_press / on_release) and a keyboard subscription, and is inert until an image is loaded. The zoom and pan survive toggling compare.

Depth estimation runs in a background Task (Message::DepthReady): the model is shared as Arc<Mutex<DepthModel>> and moved into the task, so the UI never blocks. The panel shows a persistent info line (the loaded image) and a transient status line (progress and errors, empty when idle).

Because iced 0.14 pins wgpu 27 while the engine uses wgpu 30, the two do not share a device. The engine renders to CPU pixels and hands iced an image::Handle (see decisions/0003-gui-iced.md). This is simple and robust at preview sizes; a shared-device or custom-shader path is a possible future optimization.

0001: Use Rust with wgpu for the engine

Date: 2026-10-12 Status: accepted

Context

The engine must synthesize film grain, halation, print simulation and film color shifts over images up to 16k x 16k, in 8- or 16-bit, with a live preview. The project needs a library, a CLI and a desktop GUI.

Decision

Build the engine and library in Rust on wgpu, running our own WGSL compute shaders. wgpu is the reference implementation of WebGPU and targets Vulkan, Metal and DirectX 12 from one codebase.

Alternatives considered

  • Python. Faster to prototype and stronger for the colour-science and machine-learning parts (colour-science, ONNX Runtime). Rejected as the primary language because of packaging friction, the GIL, and CPU-side cost on large 16-bit images. wgpu-py would still use WGSL, so a Python prototype remains possible for isolated experiments.
  • C++. Closest to native GPU APIs but heavier tooling and slower iteration.
  • Hybrid Rust core + Python tooling. Kept as an option for colour-science experiments and depth-model work, not as the primary language.

Consequences

  • One toolchain (Cargo) produces the library, CLI and GUI.
  • WGSL shaders written for WebGPU port to wgpu with minimal change.
  • The depth model will be called from Rust through the ort crate.
  • A Python scratchpad may be used for one-off colour-science derivations; it is not part of the shipped workspace.

Sources

  • WebGPU / wgpu (Vulkan, Metal, DirectX 12 backends).

0003: Use iced for the GUI

Date: 2026-10-12 Status: accepted

Context

The project needs a desktop GUI: grouped parameter sliders and a live preview of the effects on a selected photo. The GUI must stay pure Rust so it shares the workspace toolchain and the analog-core data model.

Decision

Use iced (retained, ELM-style) for the desktop GUI, in its own crate so its dependencies never leak into the library or CLI.

Alternatives considered

  • egui / eframe. Immediate-mode; faster to assemble a slider-and-preview editor, but a weaker fit for the structured, message-driven UI this editor will grow into.
  • Tauri + React. Would allow a WebGPU front end, but adds a web toolchain and a heavier dependency surface. Rejected to keep the stack pure Rust.

Consequences

  • iced renders through wgpu; the compute engine and the UI both use wgpu. How to share or bridge the device (a custom shader widget versus a separate compute device plus a pixel handoff) is decided during implementation and recorded there.
  • The GUI crate starts as a stub.

Addendum (2026-10-12)

iced 0.14 depends on wgpu 27, while the engine uses wgpu 30, so the two cannot share a device without pinning both to the same version. The GUI therefore runs the engine on its own device, reads back CPU pixels, and hands iced an image::Handle. This is simple and robust for a downscaled preview (longest side 900 px); a shared device or an iced custom shader widget is a possible future optimization if preview latency becomes a problem.

0004: Depth model for focus-based grain

Date: 2026-10-12 Status: accepted

Context

Focus-based grain and depth-aware halation need a per-image depth (focus) proxy, provided by a neural depth model rather than a classical focus estimate.

Decision

Use Depth Anything V2 Small (onnx-community/depth-anything-v2-small, Apache-2.0) through ONNX Runtime via the ort crate. Ship no model; download the int8-quantised ONNX file (~27 MB) on demand into the user cache and load it from there afterwards.

Alternatives considered

  • A classical focus/sharpness estimate. Cheaper and dependency-free, but much weaker on the subject/background separation the effect needs. Rejected.
  • Ship the fp32 model (~99 MB) or fp16 (~50 MB). Better numerical fidelity, but a heavy download. The int8 model is a good size/quality trade-off for a depth proxy that only modulates grain and glow.
  • Bundle the model in the repository or installer. Avoids a runtime download but bloats the repo and the binary; also complicates licensing review. The on-demand download keeps the repo small and the model attribution clear.
  • ort with a system ONNX Runtime. Avoids the build-time binary download but requires the user to install ONNX Runtime. The download-binaries default is simpler for users.

Consequences

  • The core crate depends on ort and ureq; the build fetches ONNX Runtime binaries the first time.
  • The prebuilt ONNX Runtime objects for Apple Silicon are compiled with MACOSX_DEPLOYMENT_TARGET=13.4, so .cargo/config.toml matches that target and the macOS arm64 binary requires macOS 13.4 or newer.
  • Those objects use @available, which lowers to a call to __isPlatformVersionAtLeast in Clang’s libclang_rt.osx.a. Rust final-links with -nodefaultlibs and therefore does not add compiler-rt automatically; crates/analog-core/build.rs locates the active toolchain’s archive with clang -print-resource-dir and links it explicitly.
  • The prebuilt ONNX Runtime for Windows uses the dynamic MSVC runtime (/MD). Release builds therefore set msvc-crt-static = false in dist-workspace.toml; the alternative static CRT (/MT) fails with LNK2038 and unresolved __imp_* UCRT symbols. The Windows installer requires the Microsoft Visual C++ 2015-2022 Redistributable (x64) on the target machine.
  • The first focus-based render downloads ~27 MB and can block briefly; the GUI loads the model lazily and reports progress in its status line.
  • The image is squashed to the model’s 518x518 input, an approximation documented in docs/architecture.md.
  • Offline use works after the model is cached.

Sources

  • Depth Anything V2 Small model card (Apache-2.0).

0005: GPU-resident render pipeline

Date: 2026-10-13 Status: accepted

Context

The interactive preview became slow after the depth, grain-fidelity and 16-bit milestones. The engine read back to the CPU after every compute pass (ImageComputePass copied to a staging buffer and blocked on device.poll(wait_indefinitely)), and repacked every input with as_words(). A full render is around sixteen passes, so a single preview did roughly sixteen synchronisation stalls and sixteen CPU repacks.

Decision

Keep the whole chain on the GPU. Introduce GpuImage (a GPU buffer plus its dimensions and format). Passes take &GpuImage inputs and return a GpuImage with no readback; GpuImage::read is the single synchronisation point, called once by Renderer::render. Compile passes lazily, and only the pixel-format variant actually used.

Alternatives considered

  • Pool CPU readbacks / pipeline the passes on the CPU. Keeps the CPU-mediated design and its sync stalls. Rejected.
  • Render to a texture and share the wgpu device with iced. Would avoid the final readback too, but iced 0.14 pins a different wgpu version (see 0003-gui-iced.md), so the device cannot be shared. The single readback is cheap relative to the sixteen it replaces.
  • Debounce only. Cheap, but the underlying render would still take ~0.6 s, so the preview would stay visibly laggy. Debounce was kept as a complement, not a substitute.

Consequences

  • The effect chain no longer touches the CPU between passes; measured cost at 900x600 fell from about 0.58 s to about 0.15 s.
  • Startup no longer compiles unused pipelines (lazy, per-format compilation), so launch is fast.
  • GpuImage buffers are not pooled yet; each pass allocates a fresh output.
  • Renderer::new no longer needs a GpuContext; the context is passed to render.

0006: Zoom and pan in the preview

Date: 2026-10-13 Status: accepted

Context

The GUI showed the photo as a fit-to-window image widget (ContentFit::Contain); there was no way to inspect it at 1:1 or closer. The project todo asks for scroll-to-zoom and drag-to-pan in the preview.

Decision

Draw the preview with an iced canvas (canvas::Program) and enable iced’s canvas feature. The view is a small, pure ViewTransform { zoom, pan } in crates/analog-gui/src/view.rs:

  • zoom is a multiplier on the fit-to-window scale, clamped to [1, 8].
  • pan is the image centre’s offset from the viewport centre, clamped so the scaled image never leaves a gap (and centred on an axis where it is smaller than the viewport).
  • Scrolling zooms anchored at the cursor (the image point under the pointer stays put); left-dragging pans; a “Fit” button or a double-click resets.

The canvas program only translates mouse events into new transforms and publishes them; the application stores the transform, so there is a single source of truth and the math is unit-testable.

Alternatives considered

  • A fixed-size image inside a scrollable. Reuses existing features and gets clipping for free, but the scrollable owns the wheel to pan, so it cannot also zoom; zoom-to-cursor and centring-when-smaller are awkward. Rejected.
  • An iced custom shader widget. Could keep the preview on the GPU, but is a large step beyond this change and would not change the interaction. Deferred.

Consequences

  • iced’s canvas feature is enabled; no new crate dependency is added (the canvas renderer is already part of iced).
  • The canvas clips to its bounds, which is what makes panning look correct.
  • Zooming upscales the 900 px preview proxy, so the image looks soft beyond about 1:1. Rendering a higher-resolution preview while zoomed is future work.
  • The canvas receives mouse events over its whole area, including the margin around a fit-to-window photo; this is harmless.

Sources

  • iced 0.14 canvas::Program (https://docs.rs/iced/0.14.0/iced/widget/canvas/trait.Program.html) and geometry::Frame::draw_image (iced source, graphics/src/geometry/frame.rs).

0007: Camera RAW input

Date: 2026-10-15 Status: accepted

Context

The editor’s premise is an already-developed photo, so for a long time the only inputs were JPEG/PNG/TIFF (plus PSD). Users asked to open camera RAW files directly instead of exporting a developed image first.

RAW is a much larger problem than adding a codec. A RAW file is single-channel Color Filter Array (CFA) sensor data plus metadata; turning it into a viewable image needs demosaicing, per-camera white balance and a colour matrix, a tone curve and gamma, and highlight handling. The per-camera colour matrix and levels are the hard part: without them, saturated colours and skin tones are wrong.

Decision

Decode RAW through LibRaw, a developer-grade raw engine, via the Rust wrapper libraw-rs (MIT; it vendors LibRaw 0.20.1). LibRaw ships per-camera profiles, so the result is a fully developed 16-bit sRGB image with no colour science of our own.

  • RAW files are recognised by extension (crates/analog-core/src/raw.rs) and developed to Rgba16, entering the pipeline like any other 16-bit input.
  • RAW is input only: Image::encode rejects RAW extensions.
  • Decoding is behind the raw feature of analog-core (on by default in the CLI and GUI; off for the library) so the default library build stays pure Rust and does not need a C++ compiler.

libraw-rs was chosen over rsraw because rsraw-sys always runs bindgen, which needs libclang; libraw-rs-sys ships pre-generated bindings and only needs the cc crate plus a C++ compiler. Both wrap the same LibRaw.

Alternatives considered

  • rsraw (MIT wrapper, LibRaw). Newest and best documented, but its build always runs bindgen for native targets, requiring libclang, which is not available in this environment. Rejected here; a fine choice where libclang is present.
  • Pure Rust: rawler/rawloader + demosaic. No C toolchain, and demosaic (MIT/Apache) offers professional demosaicing (AHD/VNG/PPG, Markesteijn). But the wrappers give CFA data and metadata only: we would have to implement white balance, the camera colour matrix, the tone curve and gamma, and maintain a per-camera profile database. rawler is also LGPL-2.1. Rejected as disproportionate scope with lower fidelity outside DNG.
  • DNG only, pure Rust. DNG carries its own ColorMatrix/AsShotNeutral, so a pure-Rust path is good for DNG. Rejected because it would not cover CR2/NEF/ARW, which users asked for.
  • Embedded JPEG preview extraction. Cheap, but 8-bit and already processed, so it is not real RAW. Rejected.

Consequences

  • RAW builds need a C++ compiler; the vendored LibRaw compiles in roughly 25 s on 8 cores and is cached. --no-default-features gives a pure-Rust build.
  • On Windows/MSVC, libraw-rs-sys compiles LibRaw as a static library but its build script does not define LIBRAW_NODLL. LibRaw’s headers therefore declare every API symbol as __declspec(dllimport) (libraw/libraw/libraw_types.h:102-114 in the vendored source), and defining them fails with C2491. .cargo/config.toml passes -DLIBRAW_NODLL through CXXFLAGS_x86_64_pc_windows_msvc to select a static build.
  • LibRaw is LGPL-2.1 (CDDL dual). The libraw-rs wrapper is MIT, but the linked LibRaw library keeps its own licence; downstream distributors must honour it.
  • RAW input is 16-bit, so it exercises the existing 16-bit pipeline (slower passes, larger buffers) rather than the 8-bit path.
  • Camera support is LibRaw’s (400+ models, 0.20.1); unsupported or corrupt files surface as a clear decode error.

Sources

  • libraw-rs 0.0.4 and libraw-rs-sys 0.0.4 build scripts (https://docs.rs/crate/libraw-rs-sys/0.0.4+libraw-0.20.1/source/build.rs): bindgen is an optional feature, otherwise a checked-in bindings.rs is used.
  • rsraw-sys build script (https://github.com/hexilee/rsraw): bindgen runs for host builds.
  • LibRaw (https://www.libraw.org/) for the camera database and processing.

0008: Recipe preset format

Date: 2026-10-15 Status: accepted

Context

Recipes (presets) are serialised as an XMP packet. They were previously written using another product’s namespace so presets could be exchanged with that product in both directions. Carrying a third party’s namespace and attribute prefix in this codebase ties the format’s identity to that product.

Decision

Use our own namespace and prefix:

  • namespace urn:analog:recipe:1.0, declared as xmlns:analog, with attributes prefixed analog: (for example analog:intensity, analog:grainSeed);
  • conventional file extension .analog; a bare .xmp is still accepted on import, detected by the analog: prefix;
  • public API to_recipe_xmp / from_recipe_xmp, constant RECIPE_NS.

Attribute names, ranges, defaults and the schema version are unchanged; only the namespace URI and prefix differ from the previous format.

Migration

The change is a pure text transform, so presets in the old format convert losslessly: replace the old namespace URI with urn:analog:recipe:1.0 and rewrite the old attribute prefix to analog:. A helper script in the development repository performs this for a list of files; it is not shipped, because it necessarily contains the old namespace strings.

Alternatives considered

  • Keep the previous namespace. No migration, but the codebase keeps referencing the other product. Rejected.
  • Read both namespaces, write the new one. Preserves import of old presets but keeps the old strings in the reader. Rejected for the public branch; the one-off migration covers conversion instead.

Consequences

  • Presets written in the old format no longer import; convert them once.
  • Files we write are .analog and carry xmlns:analog="urn:analog:recipe:1.0".
  • The reader is prefix-based, so any XMP carrying analog: attributes loads.
